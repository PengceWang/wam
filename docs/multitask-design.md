# 多任务目标条件化 RL —— 设计

这份文档解释 `wam/training/multitask.py` 和 `scripts/train_multitask.py` 的每一个
设计选择。每一条都对应一个**测出来的失败**，不是从论文里抄的。

## 1. 要修的是什么

单任务在线 RL 跑了 105 轮，各 checkpoint 在训练没碰过的种子上各 6000 步：

| checkpoint | 挖掘 | 原木 | **原木/挖掘** |
|---|---|---|---|
| BC 起点 | 198 | 12 | **6.1%** |
| U25 | 373 | 24 | **6.4%** |
| U50 | 382 | 16 | **4.2%** |
| U75 | 371 | 12 | **3.2%** |
| U100 | 356 | 18 | **5.1%** |

挖掘量翻倍，**7.3σ、p < 1e-12** —— 在线交互确实改变了行为。
但原木**占挖掘的比例**从头到尾没涨。多出来的量是
`picked up dirt×144, mined dirt×138, mined grass block×125`。

奖励只给原木，学到的却是"按住攻击键"。

**根因：单任务下所有拿到奖励的轨迹共享同一个共同成分。** 信用一摊开
（γ=0.999、λ=0.98、150 步窗口，一次奖励几乎同等地奖励前面 56 秒的全部动作），
策略梯度收敛到的就是那个共同成分。

## 2. 任务集合：为什么必须有一个不需要攻击的任务

| key | 指令 | 判据事件 | BC 基础率（次/千步） |
|---|---|---|---|
| `wood` | chop wood from a tree | `*log*` | 2.0 |
| `dig` | dig into the ground | dirt / grass block / sand / gravel | 18.2 |
| `leaves` | clear leaves and foliage | leaves / grass / fern / vine | 11.7 |
| `gather` | pick up items nearby | `picked up *` | 9.0 |
| `travel` | travel far from here | 位移 | — |

`travel` 是这张表里最重要的一行。**它的最优解不包含攻击。**
只要集合里有这样一个任务，"按住攻击键"就不再是所有奖励轨迹的共同解 ——
这才是多任务在这里的作用，不是"顺便多学几个技能"，
而是**给信用分配一个它现在没有的对比组**。

## 3. 每个任务的奖励必须按基础率归一化

`dig` 的自然发生率是 `wood` 的 **9 倍**（18.2 vs 2.0 次/千步）。
不归一化，`dig` 的优势幅度压倒一切。

而这不是理论担忧 —— 同一个错误已经犯过一次。`tree` 塑形用 `0.3 × 树叶 + 1.0 × 原木`，
实测树叶约 50 次/1728 步、原木约 0 次，塑形项按 **100:1** 淹没了目标信号，
原木事件直接归零。

**塑形权重要按事件频率定，不能按语义重要性拍。** 这里把每个任务缩放到
"BC 策略下每千步期望奖励 1.0"。之所以非做不可，是因为 `ppo_update` 的优势归一化
是**跨整个 batch 全局**做的（必须如此，否则会抹掉任务间差异），
所以任务间的幅度差会一比一变成梯度权重差。

## 4. 后见之明重标注只能进监督损失，不能进 PPO

PPO 的比值 `π(a|s,g) / π_old(a|s,g)` 假设数据是当前策略在**同一个目标**下采的。
把目标从 g 改成 g′ 之后，行为策略是 `π(·|s,g)` 而目标策略是 `π(·|s,g′)`，
两者不同，比值不再是那个含义，clip 的信赖域保证随之失效。

所以：

* **PPO 只用实际目标**（严格 on-policy）
* **重标注只喂自我模仿**：片段既然真的达成了 g′，那这些动作对 g′ 就是好的 ——
  直接最大化 `log π(a|s,g′)`，不需要任何重要性比值

这同时正面回答了之前三次目标条件化 BC 为什么失败
（`docs/hindsight-goals.md` §7）：那三次是拿**人类演示**做目标条件 BC，
而 BC 里没有搜索，学不会"为了拿到木头去做一串本身不像木头的动作"。
这里的片段来自 **agent 自己的成功经验**，搜索由旁边的 PPO 提供，
监督只负责把搜到的东西固化下来。

## 5. 目标敏感度：那三次失败时缺的仪表

```
goal_sensitivity = KL( π(·|s, g) ‖ π(·|s, g′) )
```

含义没有歧义：

* **≈ 0** —— 模型在**无视** goal 输入，多任务退化成"所有任务的平均策略"
* **> 0** —— goal 真的进入了决策

前三次是靠"同义句迁移率"这种下游指标才发现问题的，而那时已经训完了。
这个量每次更新都能算，第一轮就能看出来。

**它是指标，不是损失。** 做成损失会被轻易钻空子 —— 模型只要让输出随目标
随机抖动就能把它拉高，而那不是"听懂了目标"。目标该不该被使用应该由奖励说了算：
奖励依赖目标，无视目标就拿不到分。

## 6. 目标必须在采集**中途**重采

`--goal-every 75`，明显短于 `--horizon 150`。

如果一次采集里目标不变，batch 内就没有"同一状态、不同目标"的对比，
goal 这个输入拿不到区分性的梯度 —— 忽略它和使用它的损失完全一样。

## 7. 上下文长度不跟着信用视野一起收

这是整个项目最贵的一课，写在 `docs/online-rl-log.md` §3。同一份权重、
同一批种子，只改"每多少步清一次 KV cache"：

| 清 cache 间隔 | 8 | 16 | 32 | 64 | 从不清 |
|---|---|---|---|---|---|
| 原木/千步 | **0** | **0** | **0** | 1.11 | **5.00** |

8/16/32 三档合计 5400 步，原木**全零**。快方块（草、泥土、树叶，一步就碎）
完全不受影响，只有原木（约 3 秒 ≈ 7.5 个模型步）归零。

所以：

* **上下文长度** ≥ 64 步 —— 能力的硬下限，短了砍树这个动作根本做不出来
* **信用视野** γ=0.99 / λ=0.90 —— 收紧，让信用集中到事件前几秒

这两个量在代码里是**解耦**的（优势估计不需要梯度，所以视野可以很长而不花显存；
上下文长度由 cache 决定）。单任务那轮把它们绑在一起，先是绑成 8 步（没有信号），
后是绑成 150 步（信号太散）。

**清 cache 会毁能力，detach cache 不会** —— 更新时分段前向只 detach，
前向仍是完整上下文。混淆这两件事会得到"时间轴不能切"的错误结论。

## 8. 两张卡怎么用

**一张卡一个独立实验，不要 DDP。** 这个仓库在 2×RTX6000Ada 上撞过 NCCL 死锁，
而 RL 这条链路（十几个 Minecraft 子进程 + spawn 上下文 + 长 KV cache）本来就脆。
我们缺的是**对照组**，不是吞吐：

```bash
CUDA_VISIBLE_DEVICES=0 python scripts/train_multitask.py --tag A --config configs/h100-multitask.yaml ... &
CUDA_VISIBLE_DEVICES=1 python scripts/train_multitask.py --tag B --config configs/qwen3-0.6b.yaml   ... &
```

## 9. 判据

**不要看原木绝对数** —— 它会被"挖得多"污染，这正是单任务那轮差点得出错误结论的地方。

看这三个：

1. **每个任务的达成率**，各自对 BC 基础率归一化后
2. **目标敏感度**是否 > 0（否则一切免谈，模型根本没在读目标）
3. **原木/挖掘比例** —— 这个数在单任务全程没动过（6.1% → 5.1%）

评测用 `scripts/eval_parallel.py`，**默认 `--cache-reset 150`**。
不要用 8：那会让原木事件归零，整张评测表变成假阴性
（这个默认值坑过一次，一整夜的结果全是 0）。
