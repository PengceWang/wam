# 第二步：hindsight goals —— 让 goal 空间以「结果」为坐标

承接 [stage1b-log.md](stage1b-log.md)。那一份记事件预测（第一步）；这一份记
hindsight relabelling 的全过程，**包括中途发现的两个 bug 和一个被自己实验推翻的诊断**。

结论先放这里，一半成一半败：

* **成了**：GoalHead 输出的语义分离度从 0.027 提升到 0.491（18 倍）。
  模型现在看着画面能写出"我在干的这件事属于哪一类"，依据是语义而非行号。
* **没成**：那个目标**控制不了行为**。反事实注入证明它是读数不是驱动器 ——
  注入"木头"得到的木头事件与注入"泥土"、与完全不注入完全相同。补上 HER 缺掉的
  另一半（把目标喂进 goal 槽做条件化 BC）之后仍然如此。

所以第 3 节（一次因表示问题白跑的训练）和第 7 节（两次失败的驱动尝试）比第 4 节的
正结果更值得读。

---

## 1. 想法与它的前置依赖

`goal_loss` 的实现早就在仓库里，docstring 写得很清楚：

> *Hindsight relabelling: what the agent went on to achieve **was** its goal.
> targets 是「接下来几步实际发生了什么」的 LLM 嵌入（"mined oak log"），
> 所以不需要人工编写任何目标标签 —— 事件流已经说明了达成了什么，
> 而任何一条轨迹都是「到达它最终所处状态」的成功示范。*

但它一直走的是 `targets is None` 那条分支，退化成一个防数值爆炸的 L2 正则。
文档自己也承认：*"a run that never supplies targets is not training the goal head
to mean anything."*

**`hindsight_goals()` 这个函数在仓库里根本不存在**（只有 `tests/` 里一行注释提到），
和 `EventEmbedding.init_from_text` 一样，是「文档里承诺、代码里没有」的洞。

**为什么必须排在第一步之后**：「实际达成了什么」是由事件定义的。没有第一步建好的
事件管道（概念词表、`meta_info` 读取、逐窗口事件标签），hindsight 目标根本无从计算。
这两步不是并列的，是严格的先后依赖。

---

## 2. 实现

新增 `wam/data/events.py::window_events` 的第四个返回值，以及
`phrase_embedding_table`：

```
① 取数进程：从 t+1 到窗口末尾实际发生的一切，做成多热
   hindsight (B, T, 1024)

② 训练循环：乘上短语嵌入表 -> goal 空间里的一个向量
   tgt   = (hindsight @ phrase_emb) / hindsight.sum(-1)      (B, T, 1024)
   gmask = hindsight.sum(-1) > 0
   loss  = (1 - cosine(goal_tokens.mean(-2), tgt)) 在 gmask 上取平均
```

三个决定：

* **目标是"到窗口末尾"的累计，不是单步。** 目标天然跨多步。
* **什么都没发生的步被屏蔽。** 实测只有 20–40% 的步有「达成」。对着空集编目标是噪声。
* **多热留在数据侧，向量在训练循环里算。** 短语嵌入表在模型上（GPU），
  取数 worker 保持轻量。为此给 `Batch` 加了 `hindsight` 字段。

---

## 3. 第一次训练，以及它为什么是白跑的

启动权重 0.1 和 0.5 两个跑。前 100 步：

```
goal 损失：1.03 -> 0.07
```

当时的判断是"在降，合理"。**这是错的。**

写讲解材料时想把「goal 空间以结果为坐标」这句话变具体，就去测了目标向量本身的几何。
按活动类型（砍树 / 挖石头 / 挖矿 / 杀怪 / 挖土）分组，算组内与组间的余弦：

```
同类平均 0.950   异类平均 0.913   差 0.037
```

**所有目标向量几乎共线**，两两余弦都在 0.89–0.97 之间。这是 LLM 隐状态的已知性质
（各向异性：所有向量挤在一个窄锥里）。

后果：损失用的是余弦相似度，**模型只要输出那个公共方向就能拿到 0.93**，
完全不必分辨「这次是砍树还是杀怪」。回头看，症状一直摆在眼前 ——
损失 100 步就见底，掉得可疑地快。**那不是学会了，是找到了捷径。**

### 修法：减去全局均值

```
                砍树    挖石头    挖矿    杀怪    挖土
砍树           0.640   0.121   0.125  -0.042  -0.050
挖石头          0.121   0.632   0.276   0.002   0.186
杀怪          -0.042   0.002   0.097   0.469   0.051

原始:   同类 0.950  异类 0.913  差 0.037
中心化: 同类 0.511  异类 0.098  差 0.413      <- 分离度 11 倍
```

矩阵现在说得通了：砍树↔杀怪 −0.042（几乎正交），挖石头↔挖矿 0.276（都属采矿）。

`phrase_embedding_table(center=True)` 成为默认。**`seed_concept_embeddings` 保持不中心化** ——
它只是 `EventEmbedding` 的初值，之后还要被梯度继续训练，而且事件预测走 BCE 不是余弦，
未中心化已实测能拿到 mAP 0.647。不去动一个已验证有效的东西。

代价：两个跑各作废约 1.5 小时。

### 一个反直觉的对照

旧的八行指令查找表**反而分得更开**（彼此平均余弦 0.192），因为 `from_text` 只查
token 嵌入表，没经过主干那层各向异性。里面还有能解释同义句失败的细节：

```
0.845  strafe left  <->  strafe right
0.779  move forward <->  move backward
0.762  turn left    <->  turn right
```

方向相反的指令对，向量几乎一样 —— 模型能区分它们已经不容易了。

## 4. 结果

重训后各 20,000 步（全量 316,436 窗口，hidden_mult=4，batch 20）。

### 训练损失

| | 权重 0.1 | 权重 0.5 |
|---|---|---|
| actor | **1.7261** | 2.1181 |
| goal | 0.2389 | 0.1576 |
| event | 0.0007 | 0.0011 |
| flag | 0.0655 | 0.0950 |

### GoalHead 输出的语义结构（决定性指标）

不是测目标（那是标签），是测**模型学到了没有**：给不同活动的窗口，
GoalHead 写出的 goal 向量是否按活动聚类。

| 模型 | 同类 | 异类 | 差 |
|---|---|---|---|
| 对照：无 hindsight 训练 | 0.915 | 0.887 | **0.027** |
| hindsight 权重 0.1 | 0.592 | 0.101 | **0.491** |
| hindsight 权重 0.5 | 0.586 | 0.095 | **0.492** |

**分离度提升 18 倍。** 对照组的矩阵是平的（两两 0.87–0.95，完全不区分自己在干什么）：

```
权重 0.5 训练后 —— GoalHead 输出
             砍树    挖石头    杀怪    挖土
砍树        0.522   0.155   0.035  -0.071
挖石头       0.155   0.823   0.155   0.207
杀怪        0.035   0.155   0.349   0.085
挖土       -0.071   0.207   0.085   0.650
```

砍树↔挖土 −0.071（几乎相反），挖石头↔挖土 0.207（都是挖掘，确实相关）。

### 权重选 0.1

两个权重的 goal 结构几乎一模一样（0.491 vs 0.492），但 actor 差 0.39
（1.7261 vs 2.1181）。**0.5 花了更多 actor 性能，没换来更好的 goal 结构。**

## 5. 一个被自己实验推翻的诊断

在做第二步之前，我们先诊断"goal 空间是查找表"的根因，怀疑是指令编码有问题：
`GoalEncoder.from_text` 只调用 `get_input_embeddings()`，**Qwen3 的 28 层在编码指令时
一次都没被用到**。当时认为这解释了三个负结果（更大主干无改善、随机向量打平、
同义句 18%）。

改成让指令真的过一遍主干（`contextual=True`），重训 20,000 步：

* 同义句命中率 **23% -> 18%**，比不过主干还差；
* 连训练见过的指令都退化：`jump` 从 0.90 掉到 0.33，`turn left` / `strafe right`
  的按键几乎归零；
* 无关句子反而触发强动作：`eat a sandwich -> attack=0.63`。

**诊断被推翻。** 默认值改回 `False`，负结果写进 docstring。

新的判断：**问题在训练信号，不在编码方式。** 八个固定类别只需要八个可区分的点，
模型没有任何理由建立结构 —— 目标函数从未要求它泛化。这正是 hindsight 改变的东西：
目标变成成百上千种连续组合，查表蒙混不过去。

第 4 节的结果支持了这个新判断。

## 6. 顺带修掉的一个静默错位

自主性测试第一次运行时三组全崩：

```
TypeError: int() argument must be ... not 'dict'
```

checkpoint 的 config 带着 `concept_vocab_path`，而 `ConceptVocab` 期望扁平的
`{短语: id}`，`build_concept_vocab.py` 产出的是 `{"phrases": {...}, "key_to_id": {...}}`。

**这不只是探针的问题。** 读不了那个文件的话，实时环境会**重新分配 id**，
而离线训练学到的概念嵌入是按离线 id 排的 —— 同一个 id 在两边指向不同的概念，
不报错、不崩溃，只是所有事件语义静默错位。`ConceptVocab` 现在两种格式都接受。

## 7. 自主性：能描述，不能驱动

### 7.1 撤掉指令，让 GoalHead 自己填槽

三组各 6 局（每局独立进程 —— Minecraft 的世界生成线程在同进程内反复 reset 会批量
死亡，而且 ``InstanceManager`` 是类级单例，顺序跑多个 sim 会互相污染。第一次三组
跑在一个进程里，得到的排序和独立进程完全相反）。

| 配置 | n | 事件 | 挖掘 | 拾取 | 位移 | 目标稳定度 |
|---|---|---|---|---|---|---|
| A hindsight + 自写目标 | 5 | 12.6±6.7 | 8.8 | 3.8 | 21.3 | 0.962 |
| B hindsight + 钉死空目标 | 6 | 9.3±7.1 | 7.5 | 2.0 | 14.1 | 0.950 |
| C 无 hindsight + 自写目标 | 5 | 5.0±3.7 | 4.8 | 0.4 | 12.3 | **0.997** |

Welch t 检验：

```
A vs C  (hindsight 训练有没有用)   事件 +8.43±3.41  t=+2.47  差异明显
                                拾取 +3.47±1.64  t=+2.12  差异明显
A vs B  (自写目标 vs 钉死空目标)    事件 +3.27±4.19  t=+0.78  分不出来
```

**hindsight 训练有用**（拾取差近 10 倍尤其说明问题 —— 砍断只要挥手，捡起掉落物
需要走过去）。C 的目标稳定度 0.997 说明未训练的 GoalHead 输出近乎常数，即退化。

**但自写目标并不优于钉死空目标。** 无法证明"让 GoalHead 驱动"比"不让它驱动"更好。

### 7.2 反事实注入：goal 槽是读数，不是驱动器

运行中途把 goal 槽钉死成某个目标向量（构造方式与训练时完全一致），看事件分布是否
朝该方向偏。5 个种子 × 4 种注入：

| 注入 | 事件 | 木头 | 石头 | 泥土 |
|---|---|---|---|---|
| 木头 | 11.2 | 0.4 | 0.0 | 3.2 |
| 石头 | 15.6 | 0.0 | 0.0 | 4.0 |
| 泥土 | 7.4 | 0.4 | 0.0 | 3.8 |
| 不注入 | 10.8 | 0.4 | 0.0 | 2.8 |

**全线打平。** 注入"木头"得到的木头事件（0.4）与注入"泥土"、与完全不注入完全相同。
唯一变化是 attack 率从 0.611 升到约 0.71 —— 通用效应，非目标特异。

所以视频里那句 ``self-goal -> picked up oak log``，是模型对自己行为的**描述**，
不是**意图**。

### 7.3 补上 HER 的另一半 —— 仍然失败

诊断：hindsight 向量只用来训 GoalHead 的**输出**，从没进过 goal 槽当**输入**，
所以 actor 从没以这种形状的目标为条件训练过。标准 HER 是两件事一起做。

修法（``--goal-cond-prob 0.5``）：以 50% 概率把整窗的 hindsight 目标放进 goal 槽，
做目标条件化的行为克隆 —— "告诉模型你接下来会达成 X，让它预测那些真的达成了 X 的动作"。

重训 20,000 步后重跑同一注入实验：

| 注入 | 事件 | 木头 | 石头 | 泥土 |
|---|---|---|---|---|
| 木头 | 11.4 | 0.4 | 0.0 | 4.2 |
| 石头 | **1.8** | 0.2 | 0.0 | 0.0 |
| 泥土 | 11.2 | **1.0** | 0.0 | 2.2 |
| 不注入 | 7.0 | 0.0 | 0.0 | 6.4 |

**方向仍然不对，而且更糟**：注入"泥土"得到的木头事件（1.0）比注入"木头"（0.4）还多；
注入"石头"把总事件数压到 1.8（其余 7–11），等于把 agent 冻住。目标向量确实改变了
行为，但不是朝目标的方向 —— 更像分布外输入扰乱了策略。

### 7.4 判断

**这不是实现 bug，是目标条件化行为克隆的固有困难。**

hindsight 目标由同一条轨迹的未来导出，而当前帧本来就能很好地预测那个未来 ——
面前是树，接下来大概率就是"砍到木头"。目标携带的额外信息量接近零，梯度自然更愿意
走视觉通路（16 token）而不是 goal 通路（4 token）。这是 BC 里已知的"目标可从状态
推断则被忽略"。

注意 **stage 1a 的指令目标是能控制行为的**（给 "move forward" 得到 ``forward=0.91``），
用的同样是 4 个 token。所以通道带宽不是瓶颈，区别在于：指令标签是按"窗口内哪个行为
占优"分配的，goal→action 有强而干净的监督；而 hindsight 目标描述的是结果，
给定结果的动作分布要弥散得多。

**BC 里目标是输入，可以被忽略；RL 里目标是奖励，绕不过去。** ``DriveHead`` 和
``ValueHead`` 都在架构里、都没启用，而想象已验证在 5 步内可用（mAP 0.350 vs 基线 0.202）。

## 8. 还开着的

* **hindsight 目标是"到窗口末尾"的累计**，所以窗口内早期的步目标高度重合。
  固定 horizon（比如后 4 步）可能是更好的设计，未做对照。
* **`L_align` 仍未启用** —— 第三步。goal 空间现在有结构了，语言才有东西可指。
* 中心化只做了减均值，没做白化。方差归一是否还能再提分离度，未测。
