# 在线 RL 实验记录

真实环境交互训练（不用想象、不用学出来的奖励）。这份记录的重点是**被推翻的结论**——
其中两条是我自己先前写下的。

## 0. 设定

12 个并行 Minecraft 实例，实测聚合 372 tick/s = 46 模型步/秒（加上模型推理后约 26 步/秒）。
一个模型步 = 一个 8-tick 动作块 = **0.4 秒**。奖励取游戏自己吐的事件
（`mined oak log`），是真值不是预测。不 reset —— 反复 reset 会让世界生成线程批量死亡
（见 `stage1b-log.md` §1），所以走 continuing task。

## 1. 前四轮，以及它们为什么不算数

| 版本 | 挖掘 | 原木 | 位移 |
|---|---|---|---|
| BC 起点 | 9.5 | 0.833 | 17.3 |
| any_mine 奖励 | 17.3 | 0.500 | 8.2 |
| tree 塑形 | 11.5 | 0.000 | 5.2 |
| 纯 log + 世界轮换 | 9.0 | 0.667 | — |

我根据这张表写下过一个结论：「RL 一致地把砍树变差、把挖掘变好，说明它学会了站着
挖而不是走去找树」。**这个结论没有证据支持。**

评测是 6 局 × 150 步 = 900 步。BC 起点在这 900 步里一共砍到 **2 次**原木，
逐局是 `0, 0, 2, 0, 0, 0` —— 6 局中 5 局为零。上表的 0.833 / 0.667 / 0.500 / 0.000
换算成事件绝对数是 **5 / 4 / 3 / 0 次**。这个量级上的差异是泊松噪声。

**教训：先确认判据的统计功效，再跑四轮实验。** 现在评测改为并行 12 环境 × 500 步
= 6000 步（`scripts/eval_parallel.py`），并且报事件**绝对数**而不只是均值，
因为均值会把"总共 2 次"这个事实藏起来。

## 2. 它一直站在树旁边，砍的是树叶

给训练循环加了一行诊断，打印每轮实际挖到了什么（1728 步）：

```
挖到: grass×32, oak leaves×26, spruce leaves×11, tall grass×6,
      grass block×6, jungle leaves×5        ...  原木 ×0
```

橡树叶、云杉叶、丛林叶、白桦叶四种树叶天天挖 —— **它离树很近**。但 8640 步里
原木 0 次。失败模式不是"找不到树"，是"到了树跟前砍在树冠上"。

我先前"agent 学会了站着挖泥巴不走动"的诊断因此也是错的。

这顺带解释了 `tree` 塑形（`0.3 × 树叶`）为什么把原木打到 0：树叶约 50 次/1728 步、
原木约 0 次，`0.3 × 50 = 15` 对 `1.0 × 0`，**塑形项按 100:1 淹没了目标信号**。
问题不在该不该塑形，在权重差了两个数量级 —— **塑形权重要按事件频率定，不能按
语义重要性拍**。

## 3. 根因：上下文太短，砍不断一根原木

`model.step()` 每步往 KV cache 追加 83 个 token。所谓"每 8 步清一次 cache"，
实际上下文是**锯齿形**的：清完只剩 1 个时间步，涨到 8 再归零，**均值 4.5 步**。

同一个 checkpoint、同一批种子，只改上下文长度：

| 上下文 | 步数 | 原木 | 原木/千步 | 挖掘/千步 | 树叶/千步 |
|---|---|---|---|---|---|
| 每 8 步清 | 6000 | **0** | 0.00 | 36.3 | 20.3 |
| 从不清（150 步） | 1800 | **17** | **9.44** | 76.7 | 23.3 |

按 9.44/千步，6000 步该出约 57 次，实测 0 次，p ≈ e⁻⁵⁷。这不是分布偏移的渐进退化。

按方块的**破坏耗时**分组，模式非常干净：

| 方块 | 破坏耗时 | 需要的连续步数 | 短上下文下 |
|---|---|---|---|
| 草 / 泥土 / 草方块 | < 0.5s | 1 | 不受影响 |
| 树叶 | ~0.2s | 1 | 不受影响（20.3 vs 23.3） |
| **原木** | **~3s** | **≈ 7.5** | **归零** |

砍断一根原木要连续攻击约 7.5 个模型步，而平均上下文只有 4.5 步 —— **agent 砍到
一半就断片了**。快方块不需要跨步记忆，所以完全不受影响。

这一条比"信用分配视野太短"更根本，而且直接否掉了我上一版的设计：
**PPO 更新在 8 步分段上做，被优化的那个策略在结构上就砍不动树。**
分段长度不是显存权衡，是能力上限。

值得注意的是 BC 训练时 `seq_len = 8`。所以"分布内"反而是能力最差的配置，
而分布外的长上下文明显更好 —— 说明 memory 槽位没有承担起跨步记忆的职责，
真正在起作用的是原始 KV 上下文。

## 4. 两个 bug

**发送侧 BrokenPipe 无保护。** worker 死掉后主进程往关闭的管道写，
整轮训练在 320/2500 处中断。之前只给 `recv` 加了 try/except，`send` 是裸的。

**采集与更新的上下文长度不一致。** 采集时 cache 连着长满 horizon、更新时每段从
`cache=None` 重建 —— 两边看到的上下文不同，PPO 的 ratio 全是错的。这同时也是
OOM 真凶：83 token/步 × 28 层 × 12 环境 × 144 步 ≈ 16 GB。

## 5. 长视野信用分配（已实现，尚未验证）

优势估计**不需要梯度**，所以信用分配的视野和反传的跨度本来就该解耦：

```
信用分配视野   8 步(3.2s)  →  144 步(58s)      采集不带梯度，几乎不花显存
梯度反传跨度   8 步        →  8 步             显存 O(T^2) 卡在这
γ             0.99        →  0.999            0.99^130=0.27 vs 0.999^130=0.88
λ             0.95        →  0.98             更靠真实回报，绕开没训练过的价值头
每次更新样本   96          →  1728
```

实现是梯度按分段累积（`ppo_update` 收一个 chunk 列表），优势在整个 horizon 上算、
**跨所有分段一起归一化** —— 每段各自归一会抹掉段间差异，而那正是长视野带来的信息。

但由 §3，分段长度必须先解决：8 步的分段砍不动树，长视野也救不了。
